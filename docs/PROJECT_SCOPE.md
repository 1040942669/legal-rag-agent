# 项目边界与版本决定

> 决定日期：2026-10-21。仓库所有者授权维护者直接拍板。本文件是之后所有改动的准绳。
>
> **2026-10-22 起解除范围冻结（D9）。** 第 3 至 6 节记录的是 v1.1.1 的冻结状态，作为历史保留；v1.2 的开发按第 8 节进行，效果在留出集上达标后再冻结。

## 1. 这个项目是什么

一个基于**固定公开语料**的中国法律条文检索与问答工程项目。它要证明的不是"效果有多好"，而是四件事：

1. **数据可复现**：语料是一个公开数据集的固定版本，236 个文件逐个 SHA-256 校验，任何人都能下载到完全相同的文本。
2. **检索可解释**：自研中文 BM25、法律名与条号精确查表、可选向量检索，每个结果都有 ranking trace。
3. **评测可审计**：每个数字都写明用了哪份语料、哪套题、有什么局限，负结果照样保留。
4. **生成有边界**：证据不足或请求越界时，系统可预测地停止，而不是编一个答案。

| D2 | **唯一语料**：Hugging Face `Kuugo/Chinese_Law` revision `a829f47d` 的 236 个文件，逐字节一致，见 [语料清单](../configs/corpus/kuugo_chinese_law_a829f47d.manifest.json) | 旧的本地快照里 17 个文件被改过、12 个文件不在该数据集中。v1.1.1 查明它们大多是补录脚本从另一个公开数据集按标题取来的，取数时没有校验版本：刑法拿到的是已被取代的 2009 年版（盗窃罪还写着死刑），公司法是 2023 年修订前的旧版。版本不对、未经校验的文本不能进入冻结版本 |

| D4 | **检索重构止于 R2**；R3（BM25F 重写）、R4（服务层索引缓存）、R5（混合检索与重排调优）取消 | R3、R4 是性能和架构改进，不改变正确性；R5 需要 GPU 或付费 API，而且没有留出集就无法证明收益 |

| D7 | **流程简化**：分支 -> PR -> CI 全绿 -> 合并；只有用户可见的变化才打 Tag | M0-M6 的 STATE、回执、交接文档已经比代码本身还重。它们作为历史保留，不再继续维护 |

| D8 | **模型调用一律走 SiliconFlow，本机不跑本地模型**（v1.0.0 发布后由所有者追加）。向量检索默认用 `BAAI/bge-m3`，重排用 `BAAI/bge-reranker-v2-m3`，两者在 SiliconFlow 上免费；生成默认用 `deepseek-ai/DeepSeek-V4.1-Flash`（收费，在 SiliconFlow 列出的 DeepSeek 型号里最便宜）；LLM judge 用另一家厂商的 `zai-org/GLM-5.3-Flash`，不让模型给自己的回答打分。本地模型的代码保留，只有显式指定才会加载。允许在冻结语料上把预先列出的组合（向量检索、多路召回、重排、向量文本拼接法律名和条号）各测一次，只报告、不调参，默认检索器仍是 BM25；结果见 [v1.1.0 设计消融](../reports/retrieval/V1_1_SILICONFLOW.md) | 本机内存 16 GB，本地 embedding 模型或 Ollama 和其他程序一起跑会把内存占满；这几个开源模型 SiliconFlow 都有托管。补测向量检索是 v1.0.0 最大的空缺：生活化描述的 Hit@5 只有 0.444，需要知道向量检索在同一份语料上能补上多少 |

## 4. v1.1.1 冻结时明确不做（历史，v1.2 的规则见第 8 节）

- 不再补录、抓取或手工修改法律文本。需要更多法律时，换用一个新的公开版本并生成新的语料清单，作为新版本发布。
- 不再新增数据库、队列、框架、Agent 或界面。
- 不在本机运行本地模型（D8）。不重跑历史上的多模型生成和 LLM judge 实验；向量检索和重排只按 D8 在冻结语料上各测一次。历史数字保留为历史，并标明条件。
- 不在开发集上继续调参或挑选配置。
- 不合并 PR #31 的任何部分。

## 5. v1.1.1 冻结时接受的已知局限

这些问题都已确认、已写明。v1.1.1 不再修；v1.2 要处理的项目见第 8 节：

- **语料覆盖**：236 个文件全部是全国人大及其常委会通过的法律，截止 2025-01-01；不含宪法、国务院行政法规（如工伤保险条例）和司法解释，之后的修订也不在内。
- **许可证**：数据集最初的版本在 README 中声明 `license: mit`，2025-04-24 的两次 README 改写删掉了这行，当前版本没有许可证声明。仓库只保存语料清单，不分发法律文本。
- **评测集**：开发集由大模型生成，未经法律专业审核，被反复用于开发；没有留出集。合成条号集的问题直接使用语料标题，精确查表必然命中，它只证明解析路径通了。
- **向量检索只在开发集上测了一次**：v1.0.0 时 dense、RRF 没有在冻结语料上重跑；v1.1.0 按 D8 用 SiliconFlow 补测了一次（见 [v1.1.0 设计消融](../reports/retrieval/V1_1_SILICONFLOW.md)），每种组合只测一次、参数都是默认值，仍是开发集数字。历史上的 dense、RRF 数字来自旧语料和修复前的解析器，不能与之直接比较。
- **API 模型无法固定版本**：SiliconFlow 不提供模型版本号，同名模型以后可能被替换，所以向量缓存只能记录提供方和模型名，不能像语料那样逐字节核验。服务层的向量检索仍只接受能核验版本的本地模型，因此服务层只用 BM25。
- **服务路径**：每个请求都重新构建一次 BM25（本机约 1 秒），而且使用默认参数而不读配置。冻结语料不含废止法律，所以降权参数的差异不影响结果。
- **条号解析**：不支持俗称（如"民诉法解释"）、条号范围展开和"本法"指代；简称可能出现在普通词语里被误识别（"有限责任公司法定代表人"会识别出"公司法"）。
- **置顶只在 BM25 内生效**：RRF 融合和 reranker 可能把精确命中排下去。默认配置不开这两项。
- **查询分析与证据检查**：`query.py` 的常用法律名单和证据检查中的法律名覆盖仍是子串判断，只用于路由、风险标记和证据提示。

## 6. v1.1.1 冻结期间什么情况才开新版本（历史）

| 触发条件 | 版本 | 要求 |
| --- | --- | --- |
| 修复会给出错误法律依据的正确性 bug | `v1.0.x` | 回归测试先行；基线数字变化要写进 CHANGELOG |

除此之外的想法记在 issue 里，不进代码。

## 8. v1.2 开发计划（2026-10-22 起）

目标：在留出集上把检索和回答的效果做好，再冻结。顺序是先立规范、再重构、再提升效果，不推倒重来：现有测试和 CI 是重构的安全网。

| 阶段 | 内容 | 完成标准 |
| --- | --- | --- |
| 0. 规范 | 本节决定；[核心架构说明](ARCHITECTURE_CORE.md)；评测协议；把 v1.1 的消融脚本收进仓库，成为正式命令 | 所有者能看着架构说明讲清每个机制；一条命令复现 v1.1 的全部数字，并输出 token 用量 |
| 1. 留出集 | 按下面的评测协议生成并冻结 | 留出集入库，只在阶段 4 使用 |
| 2. 重构核心检索 | 精确查条号改成检索前的独立通道，不被融合和重排打乱；按查询类型路由做成正式检索器；只保留一处配置来源；条文 ID 不再依赖语料的绝对路径；删除已证明无用的旧路径 | 测试全过；开发集数字不退化 |
| 3. 提升效果 | 向量模型、重排模型、口语改写等在开发集上比较和筛选，模型调用不设费用上限，但每批汇报用量 | 每个候选方案都有配对 bootstrap 结果 |
| 4. 冻结 | 只在留出集上评一次，按结果定默认配置 | 达到所有者认可的目标，打新的版本标签 |

**评测协议。** 开发集（现有的 `legal-eval-dev-v1` 与合成条号集）用来挑方案，可以反复用；留出集只在阶段 4 评一次，结果不再用来改方案。留出集可以由模型生成，但要满足三条：

1. 生成后立即冻结入库，开发过程中不看、不调；
2. 出题时不给模型看条文：先生成"人物与生活场景"，再用这个人的口吻提问；出题模型与系统使用的模型不是同一厂商；
3. 标准答案单独标注：用多套检索器的前 20 名合并成候选池，由另一个模型逐条判断并写出理由，所有者抽查 20 到 30 道并报告一致率。

另由所有者亲手写约 20 道题，作为对照：模型版与人写版的差距本身就是一个结论。
