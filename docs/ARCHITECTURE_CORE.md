# 核心架构说明（v1.2 开发基线）

> 写于 2026-10-22，对应提交 `9944030`（v1.1.1）。这份文档只讲**一次问答请求经过的核心链路**：每个机制做什么、为什么这样做、怎么验证、有什么已知问题。改动核心机制之前先改这份文档，由仓库所有者确认。服务层（FastAPI、PostgreSQL、Celery）只在最后一节简要说明。

## 1. 一次请求经过哪些环节

```
用户问题
  │
  ├─ ① 查询分析   legal_rag/query.py · query_parser.py
  │      风险标记（检索前拒答）、法律名与条号解析
  │
  ├─ ② 检索       legal_rag/retrieval.py · rerank.py
  │      BM25（默认）/ 向量 / RRF 多路召回 / 可选重排
  │      带条号时：（法律，条号）完全一致的条文置顶
  │
  ├─ ③ 证据检查   legal_rag/evidence.py
  │      问题提到的法律和条文找到没有；不够就补充检索或停止
  │
  ├─ ④ 生成       legal_rag/chat.py · llm.py
  │      只能引用编号化证据 [S1]…[Sk]，输出固定结构的 JSON
  │
  └─ ⑤ 校验       legal_rag/verifier.py
         编号是否存在、是否伪造、是否越出本次检索范围；回答模式是否与证据状态一致
```

数据在请求之前就准备好：

```
固定语料（236 个文件，SHA-256 清单）
  → 解析成条文（legal_rag/data.py）
  → 切成检索单元，一条一个（legal_rag/chunking.py，article 策略）
  → BM25 在请求时现场建；向量缓存离线建好（legal_rag/embeddings.py）
```

## 2. 数据层

### 2.1 固定语料

- **做什么**：只用 Hugging Face `Kuugo/Chinese_Law` revision `a829f47d` 的 236 个文件。仓库提交逐文件大小和 SHA-256 的清单（`configs/corpus/kuugo_chinese_law_a829f47d.manifest.json`），`fetch-corpus` 下载并校验，`verify-corpus` 核对本地文件，`retrieval-audit --corpus-manifest` 在语料不一致时拒绝运行。
- **为什么**：旧的本地语料混进了补录脚本按标题取来的文件，取数时没校验版本，刑法拿到的是已被取代的 2009 年版。法律文本有时效，说不清版本，检索再准也会给出错误依据。
- **怎么验证**：`tests/test_corpus_manifest.py`；每次评测带 `--corpus-manifest`。
- **已知问题**：不含宪法、行政法规和司法解释；数据集本身没有施行日期字段，做不了"按日期检索有效版本"。

### 2.2 条文解析

- **做什么**：识别每部法律的"第X条"行头，把文件切成一条一条的条文。条号行头只认行首，或者句末标点之后、并且后面带分隔符的位置；章节和目录行丢弃；"第X条之Y"（如刑法第一百三十三条之一）单独成条。
- **为什么**：早期版本在行内只要遇到"第X条"就切，把"依照本法第二百六十四条的规定"切成了假条文，被引用的条文丢了后半段。旧语料上有 676 条这样的碎片，而"法律名和条号对上就算命中"的指标把它们也算成了命中。
- **怎么验证**：`legal_rag/corpus_integrity.py` 统计同号冲突、引用碎片、未终止条文、粘连章节标题；冻结语料上分别是 3 组（源文件畸形行）、0、12、0。测试在 `tests/test_data.py`、`tests/test_corpus_integrity.py`。

### 2.3 检索单元

- **做什么**：默认 article 策略，一条法条就是一个检索单元，正文前加上"《法律名》第X条规定，"。另有 neighbor、long_split、fixed_chars 三种策略，只用于实验。
- **为什么**：条号引用、来源展示和证据检查都依赖条文粒度；旧语料上按窗口或固定字数切，Hit@5 的差异都在置信区间内。
- **已知问题**：`chunk_id` 由条文 ID 计算，而条文 ID 里带着源文件的绝对路径，所以同一份语料放在不同目录会得到不同的 ID 和语料指纹，向量缓存不能跨目录复用。v1.2 阶段 2 修。

## 3. 查询理解

### 3.1 风险标记与检索前拒答

- **做什么**：`query.py` 用关键词给问题打风险标记：情绪化、诉讼策略、违法帮助、非法律问题、医疗金融建议。后四类在检索之前就用模板拒答，不调模型。
- **为什么**：这几类请求不该由法律条文检索系统回答；在检索前停，成本最低，也不会被检索结果带偏。
- **已知问题**：只是关键词规则，误杀率和漏放率没有系统测过；开发集里只有 12 道拒答题。

### 3.2 法律名与条号解析

- **做什么**：`query_parser.py` 从语料标题自动生成别名表（全称、去掉"中华人民共和国"的简称、去年份、〈〉嵌套写法），能对应多部法律的简称直接丢弃。匹配时先做全角半角规范化，按别名长度从长到短取互不重叠的匹配；书名号里只认完整标题。条号不管写成中文、阿拉伯还是全角数字，都转成整数再写回语料写法。条号归属同一句里离它最近的前置法律，否则归属问题里唯一的那部法律。
- **为什么**：子串匹配会让"保险法"命中"社会保险法"；阿拉伯数字条号以前几乎全部检索失败（旧语料合成题里 205 条只有 2 条排第一）。
- **怎么验证**：`tests/test_query_parser.py`；合成条号集 708 条（236 部法律 × 全称、简称、阿拉伯数字三种写法）。
- **已知问题**：不认俗称（"民诉法解释"）、条号范围只取两端、不解析"本法"指代；简称可能出现在普通词语里被误识别。

## 4. 检索

所有检索器由 `legal_rag/cli.py` 的 `create_retriever` 构造，服务层和实验用的是同一套检索器类。

### 4.1 BM25（默认）

- **做什么**：自研中文 BM25（k1=1.5，b=0.75）。分词取单字、相邻两字、英文数字串、书名号里的标题、"第X条"字样。在 BM25 分数之上，法律名与解析结果相等加 40，条号相等加 80，（法律，条号）与条文完全一致再加 1000，并按用户提到的顺序置顶。
- **为什么**：框架默认的 BM25 不处理中文分词，旧语料上只有 0.111；法律检索需要书名号标题和条号这些特征，还需要每个结果的打分明细（trace）。
- **怎么验证**：v1.0.0 基线开发集 Hit@5 0.723；带条号的查询 24 道全中；合成条号集全部排第一。
- **已知问题**：每次查询都扫描全部 19276 条（约 300 毫秒）；精确查表靠一个大加分常数实现，分数语义混在一起，融合和重排都不保证维持置顶（实测重排后条号查询排第一从 100% 降到 93.9%）。v1.2 阶段 2 改成检索前的独立通道。

### 4.2 向量检索

- **做什么**：文档向量离线建好存成缓存，查询时调用 SiliconFlow 的 embedding 接口算查询向量，和全部文档向量做点积（已归一化，即余弦相似度）。默认 `BAAI/bge-m3`（免费）；可选 `Qwen/Qwen3-Embedding-4B`（收费）；`*_meta` 变体在条文前拼上"法律名 条号"。
- **为什么**：大白话问题和条文措辞对不上（"公司周末让我加班"和"休息日安排劳动者工作"），词面检索解决不了。
- **怎么验证**：开发集 Hit@5，bge-m3 0.921，Qwen3 0.980；生活化描述类从 BM25 的 0.444 升到 0.815 和 0.926。缓存记录模型、前缀、拼接开关和语料指纹，`cache-health` 检查不一致就拒绝使用。
- **已知问题**：向量在精确条号上很差（条号集只有 17% 到 27% 排第一）；API 模型无法固定版本；服务层只接受能核验版本的本地模型，所以服务层不用向量检索。

### 4.3 RRF 多路召回

- **做什么**：BM25 和向量各取前 3 倍深度的候选，按 1/(60+名次) 打分相加后重排。
- **为什么**：本意是两路互补。
- **实测**：两种向量模型都比向量单路低 7.9 个点。两路质量差太多时，弱的一路排在前面的错误结果会被拉进前 5。v1.2 不再把它当作改进方向，改为按查询类型路由。

### 4.4 重排

- **做什么**：取上游前 20 名，交给 SiliconFlow 的 `BAAI/bge-reranker-v2-m3` 打分后重排（`SiliconFlowReranker`，一次请求给全部候选打分）。
- **实测**：五组加重排都没有显著提升；在 Qwen3 向量之上反而降了 5.9 个点。加重排以后所有组合的 Hit@1 都在 0.64 到 0.67，说明前几名由重排模型决定，而它不如 Qwen3 向量本身。v1.2 阶段 3 试更强的重排模型。

### 4.5 按查询类型路由（v1.2 待实现）

- **设想**：查询解析出（法律，条号）就走精确查表，否则走向量检索。
- **依据**：v1.1 的事后模拟中，开发集与向量单路一样好，条号集全部排第一。规则是看了开发集结果才提出的，必须在留出集上验证。

## 5. 证据、生成与校验

### 5.1 证据检查

- **做什么**：`check_evidence_sufficiency` 判断问题提到的法律和条文在检索结果里有没有（条号先规范化再比较）；不够就生成补充查询，或者按模板说明缺什么。
- **为什么**：法律场景里答错比不答代价大；资料不足要明确停下来，而且说清缺哪部法、哪一条。
- **已知问题**：法律名覆盖仍是子串判断，只用作提示。

### 5.2 生成

- **做什么**：检索结果按名次编成 `[S1]`、`[S2]`……放进提示词。模型必须输出固定结构的 JSON：回答正文、回答模式（正常回答、资料不足、需要澄清、超出范围）、逐条主张及其引用的证据编号、局限说明、澄清问题。默认模型 `deepseek-ai/DeepSeek-V4.1-Flash`（SiliconFlow）。
- **已知问题**：提示词里带了源文件在本机的绝对路径，没有用，还暴露了目录结构。

### 5.3 校验

- **做什么**：`verify_answer` 检查每条主张引用的编号是否真的在本次检索结果里；把各种 Unicode 括号、全角 S、零宽字符都按"形近"处理，不是标准 `[S数字]` 的一律判为格式错误；引用的证据必须在本次请求允许的数据范围里；回答模式要和证据状态一致。任何一项不过，就降级成兜底回答。
- **已知问题**：只能查编号对不对，查不了条文内容是否真的支持结论；这一块由离线的 LLM 评审（`zai-org/GLM-5.3-Flash`，与生成模型不同厂商）度量。

## 6. Agent 运行时（服务路径）

服务路径把第 1 节的链路放进一张 LangGraph 有界状态图（`legal_rag/harness/`）：

```
analyze_query → route →（拒答走模板）
              → retrieve → merge_evidence → check_evidence
                    ↑                        │ 不够且预算还有
                    └──── plan_followup ←────┘
              → generate → verify → persist_result
```

- **模型只在两处出现**：规划补充查询、组织回答。停不停、能查什么，由代码决定。
- **预算**：最多 2 轮检索、每轮 3 个查询、8 次工具调用、4 次模型调用、4 次嵌入调用、每个外部操作重试 1 次、从受理起 90 秒的绝对期限。每次外部调用之前先在 PostgreSQL 账本里预留额度，只扣不退。
- **工具**：只有 4 个只读工具（`search_laws`、`get_article`、`get_neighbors`、`inspect_evidence_metadata`）；用户、快照、数据库连接、SQL 等字段不允许出现在工具参数里，由服务端从冻结状态填入，所以证据里的提示注入改变不了检索范围。
- **停止原因**：证据充分、策略拒答、需要澄清、检索轮次用完、工具次数用完、规划不出新查询、外部调用结果未知，每次结束都写明。
- **恢复**：LangGraph 的 PostgreSQL 检查点保存图的进度；应用侧另有检查点指针、预算账本和外部调用记录。进程在"调用已发出、结果未落盘"时挂掉，这次调用记为"结果未知"，不静默重试。租约加递增的 epoch 让过期的 worker 写不进状态。
- **已知问题**：补充检索这条链路的效果没有单独评测过；服务路径每个请求都重建一次 BM25，且用默认参数而不读配置。

## 7. 评测

- **检索审计** `legal-rag retrieval-audit`：直接调用检索器取前 20 名，输出 Hit@1/3/5/10/20、MRR@10、全部目标条文召回、分题型指标、标准答案歧义状态和延迟；可同时做语料完整性审计；带 `--corpus-manifest` 时语料不一致就拒绝运行。
- **题集**：
  - 开发集 `eval_cases/legal_eval_dev_v1.jsonl`：113 条，其中 101 条有标准答案。来自大模型生成的 v3，在冻结语料上逐条复核后删掉 7 条。
  - 合成条号集 `eval_cases/citation_lookup_v2.jsonl`：708 条，只证明三种写法的解析路径都通。
  - 留出集：v1.2 阶段 1 建立，规则见 [项目边界](PROJECT_SCOPE.md) 第 8 节。
- **比较方法**：单个数字给 bootstrap 95% 区间；两个方案比较时，对同一道题的差值做配对 bootstrap，区间不跨 0 才算有差异。
- **已知问题**：v1.1 的消融靠会话临时目录里的脚本完成，没有收进仓库；v1.2 阶段 0 做成正式命令，并记录 token 用量和费用。

## 8. 配置

- 运行时读 `configs/default.yaml`，并合并到 `legal_rag/config.py` 里的内置默认值之上；不带路径调用 `load_config()` 只返回内置默认值。
- 两处目前手工保持一致，有测试检查关键默认值（全部走 SiliconFlow、评审与生成不同厂商）。
- **已知问题**：两份默认值是重复的，迟早会不一致；服务路径的 BM25 参数不读配置。v1.2 阶段 2 收成一处。

## 10. 已知问题与 v1.2 处理计划

| 问题 | 影响 | v1.2 阶段 |
| --- | --- | --- |
| 精确查表是 BM25 里的加分常数 | 融合和重排会把精确命中排下去 | 2：改成检索前的独立通道 |
| 没有按查询类型路由 | 向量检索在条号查询上很差，BM25 在大白话上很差 | 2：做成正式检索器；4：留出集验证 |
| `chunk_id` 依赖语料的绝对路径 | 同一份语料换目录后向量缓存不能复用 | 2：改用相对于语料根目录的路径；数据库快照的 ID 随之变化，要重新导入 |
| 两份默认配置、服务路径不读配置 | 改了一处，另一处不变 | 2 |
| 提示词带本机绝对路径 | 无用、暴露目录结构 | 2 |
| 重排模型比 Qwen3 向量弱 | 加重排反而变差 | 3：试 Qwen3-Reranker、大模型列表式重排 |
| 大白话改写没有可靠方案 | 历史上规则改写反而变差 | 3：试 HyDE 等，先在开发集上证明 |
| 消融脚本不在仓库里 | 结果难以复现，用量没有记录 | 0：做成正式命令 |
| 没有留出集 | 所有数字都偏乐观 | 1 |
| 补充检索的效果没评测过 | 不知道 Agent 多查一轮值不值 | 3 |

## 11. 怎么改这份架构

1. 先在本文件里写清改什么、为什么，以及怎么验证；
2. 在开发集上用配对 bootstrap 证明不退化或有提升；会改变默认行为的，等留出集；
3. 分支 -> PR -> CI 全绿 -> 合并；数字变化写进 CHANGELOG。
