# 演示线优化方案

> 2026-10-23。本方案负责"能用、够快、看得见"：一个本地网页，查询能在短时间内得到回答，并展示链路节点、检索材料和所用模型。检索效果的提升按[项目边界](PROJECT_SCOPE.md)第 8 节另行推进；本方案不改检索默认配置，也不在开发集上调检索参数。执行流程按[项目管理流程](PROJECT_MANAGEMENT.md)。

## 1. 验收目标

打开本地网页，输入一个法律问题：

1. 服务预热后，BM25 检索结果在 2 秒内出现在页面上。
2. 含生成与校验的完整回答，中位数在 10 秒内返回。
3. 页面能看到：每个节点的状态与耗时；检索到的条文全文、分数、重排前后的排名；用到的检索器、向量模型、重排模型、生成模型，以及 token 用量。
4. 模型答对、引用编号也正确时，不再被校验器替换成保守回答。

## 2. 现状

主仓库里有一个未提交的 Gradio 演示（`demo/app.py`），2026-10-22 的运行记录（`artifacts/demo_trace.jsonl`）暴露了下面的问题：

| 问题 | 证据 | 影响 |
| --- | --- | --- |
| 生成耗时 20.7 到 24.3 秒 | 运行记录中的 `stages_ms` | 等待太久 |
| 正确引用 `[S1]`、`[S2]` 的回答被判为 `citation_ids_invalid`，换成保守回答 | 运行记录中的 `verifier_rejected` | 用户看不到正确答案 |
| 送给模型的条文不完整，模型自述"[S1] 在第五项处截断" | 同上 | 回答缺项 |
| 首次查询要 1.3 到 1.7 秒构建检索器 | `准备检索器` 耗时 | 第一次查询慢 |
| Gradio 不在项目依赖里，靠全局 Python 加拼接 `PYTHONPATH` 运行 | `demo/run.ps1` | 换一台机器就跑不起来 |

## 3. 技术决定

| 决定 | 理由 | 放弃的方案 |
| --- | --- | --- |
| 界面用 FastAPI、单个静态 HTML 页面和 SSE | FastAPI 和 uvicorn 已在 `service` 可选依赖里，不加新依赖；SSE 可以逐节点推送状态；不需要前端构建 | Gradio：不在项目依赖里，也难以展示节点链路 |
| 先在进程内调用 `LegalChatAssistant` 的分阶段方法，不依赖 PostgreSQL | 服务路径要先把冻结语料导入快照，一个晚上做完风险太大；分阶段方法与服务用的是同一套核心逻辑 | 直接接 M5 API：放到阶段 D2 |
| 服务启动时预建检索器 | 首次查询不再付构建成本 | 每次请求现建 |
| 生成提速先调参数（关闭思考模式、限制输出长度、精简提示），仍不达标再换 SiliconFlow 上的其他模型 | 先找到慢在哪里，再决定是否换模型 | 直接换模型：不知道原因，换了也可能一样慢 |
| 换模型时不选 `zai-org` 的模型 | LLM judge 是 GLM-5.3-Flash，生成和评审不能是同一家（项目边界 D8） | |

## 4. 第一批工作（Orca 监督模式，各用一个新 worktree 和分支）

| Worker | 负责的文件 | 不许改 | 验收 |
| --- | --- | --- | --- |
| A：网页界面 | 新建 `legal_rag/web/`、`tests/test_web_*.py`；`pyproject.toml` 的入口；`.gitignore` | `chat.py`、`llm.py`、`verifier.py`、`evidence.py`、`configs/`、文档 | 离线测试覆盖事件顺序；本机实测预热后检索结果 2 秒内出现；页面四类信息齐全 |
| B：快而对的回答 | `legal_rag/chat.py`、`llm.py`、`verifier.py`、`evidence.py`、`configs/default.yaml` 及对应测试 | `legal_rag/web/`、`pyproject.toml`、文档 | 误判有回归测试；条文完整送入提示；固定问题上的生成耗时实测表，中位数不超过 8 秒 |
| 协调者（主会话） | 文档、CHANGELOG、README，本地集成分支 | 业务代码 | 两个分支合并后端到端实测，启动服务供所有者查看 |

接口约定：A 只依赖 `prepare_question`、`retrieve_turn`、`generate_turn`、`verify_turn`、`commit_turn` 和它们返回对象的现有字段。B 可以加字段，不能改名或删除字段。

所有提交只留在本地，不推送、不开 PR，等所有者看过再决定。

## 7. 第一批结果（2026-10-23）

两个 worker 各自完成后，在本地集成分支 `1040942669/v1.2-web-demo` 上合并。集成时发现一处接缝问题：网页为了按请求统计 token，自己构建生成客户端，没有用上关闭思考的新默认值，生成仍要 12 到 67 秒。修复后，北京时间 04:30 前后在网页服务上实测：

| 验收目标 | 结果 |
| --- | --- |
| 预热后 BM25 检索结果 2 秒内出现 | 0.15 到 0.37 秒；向量检索 0.72 秒 |
| 完整回答中位数 10 秒内 | 7 道题 2.6 到 7.0 秒，中位数约 3.4 秒 |
| 页面显示节点、材料、模型和用量 | 已实现，浏览器实测通过 |
| 引用正确的回答不再被替换 | 7 道题中 6 道送达有据回答；押金题检索没找到押金条款，模型正确地回答资料不足 |

遗留问题：

- 耗时都在凌晨低峰时段测得，白天高峰可能更慢。届时如果仍然慢，就做 D3（流式生成）。
- 生活化描述的召回问题（例如押金题）属于检索效果，按项目边界第 8 节推进。
- `legal_rag/judge.py` 只把每条证据的前 500 字交给 LLM judge，现有索引里有 81 条超过 500 字，需要另开 Issue 处理。
