# 项目复盘：法律 RAG 的检索问题是怎么一层层找出来的

> 写于 `v1.0.0` 冻结时（2026-10-21），`v1.1.0`（2026-10-22）补充了第 6 节的设计消融。按"问题 -> 证据 -> 改动 -> 结果 -> 代价"记录，负结果和没解决的问题一起写出。数字的完整条件见各节链接的报告。

## 1. 起点

- 项目：基于中国法律条文的检索与问答。默认检索器是自研中文 BM25，可选向量检索、RRF 融合和重排序。
- 评测集 v3：120 条，10 种题型，108 条带"法律 + 条号"标准答案，题目由大模型生成。
- 2026-06 的报告：BM25 Hit@5 0.704，Qwen3-Embedding-4B 向量检索 0.981。看上去 BM25 尚可、向量检索很强。
- 疑点：使用中感觉检索"问题挺多"，但指标没有反映出来。

## 2. 第一层：指标的定义藏住了解析器 bug（R0、R1）

**做法。** 先审计语料，而不是先调 BM25 参数：同法同条号冲突、被截断的条文、混进正文的章节标题，以及疑似从引用处切出来的假条文。

**发现。** 语料里有 38 个文件没有书名号行头，格式是"第N条　正文"。解析器在这些文件的行内只要遇到"第X条"就切一刀，于是"依照本法第二百六十四条的规定定罪处罚"被切成一条假的第二百六十四条，被引用的那一条反而丢了后半段：

| 指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 疑似引用碎片 | 676 | 0 |
| 同法同条号冲突 | 427 组 | 3 组（源文件畸形行） |
| 未以终止标点结尾的条文 | 1076 | 10 |
| 正文粘连章节标题 | 361 | 0 |

例如劳动合同法第四十六条（经济补偿的七种情形）修复前只剩"……支付经济补偿：（一）劳动者依照本法"。

**为什么指标看不出来。** 命中的判定是"法律名对上、条号对上"，假碎片也算命中。v3 的 108 条标准答案里，有 18 条在语料中对应多条同号记录，命中可能落在碎片上。

**改动。** 条号行头只认行首，或句末标点之后且后面带分隔符的位置；章节、目录行直接丢弃。

**结果。** v3 Hit@5 0.704 -> 0.713，变化在置信区间内。这一步的价值是正确性，不是分数。详见 [R0/R1 报告](retrieval/R0_R1_baseline.md)。

## 3. 第二层：评测集覆盖不到的查询写法（R2）

**做法。** 从语料自动生成合成条号查询：每部法律抽一条，用全称、简称、阿拉伯数字三种写法提问。

**发现。**

- 阿拉伯数字条号（"刑法第264条"）Hit@1 只有 2/205：条号加权只认中文数字。
- "保险法第九十八条"排第一的是社会保险法：法律名用的是子串判断，`"保险法" in "中华人民共和国社会保险法"` 成立。"能源法"和"节约能源法"、"环境保护法"和"海洋环境保护法"同理。
- v3 的条号题全用中文数字和不会混淆的法律名，所以完全看不到这两个问题。

**改动。** 新增统一的查询解析器：用语料标题生成唯一的别名表（全称、去"中华人民共和国"简称等），最长匹配、精确等值；条号一律转成整数再规范化；查询中的（法律，条号）与条文完全一致时排在最前。

**结果。** 合成集 Hit@1 0.658 -> 1.000，v3 的 108 条名次逐条不变。注意这个 1.000 有一部分是构造决定的：合成题直接用语料标题，精确查表必然命中。详见 [R2 报告](retrieval/R2_citation_resolver.md)。

## 4. 第三层：数据来源本身不可信（v1.0.0）

**做法。** 把本地语料逐文件与公开数据集 `Kuugo/Chinese_Law` 原版比对 git blob 哈希。

**发现。** 本地 205 个文件里只有 176 个与原版一致；17 个被改过，12 个原版根本没有，另有 43 个原版文件本地缺失。v1.0.0 时这些文件找不到来源记录；v1.1.1 追查到它们大多来自一个补录脚本：它从另一个公开数据集 twang2218/chinese-law-and-regulations 按标题取条目写入，29 个里有 24 个与该数据集逐字一致（换行符除外）。脚本只按标题取第一条命中，没有看数据集自带的状态和施行日期，所以刑法取到了已被取代的 2009 年版，而状态为"有效"的 2020 年修正版就在同一个数据集里。抽查结果：

- 刑法是 2011 年刑法修正案（八）之前的旧文本，盗窃罪还写着"处无期徒刑或者死刑"；整部文件没有一条"第X条之Y"，也就没有危险驾驶罪。
- 公司法是 2023 年修订前的旧版。
- 刑事诉讼法末尾混进了网页残留"<< 返回首页 / 相关文章"。
- 项目 README 写的"数据卡标注 Apache-2.0"在主数据集的历史里找不到：它最初声明的是 MIT，后来 README 改写时删掉了，当前版本没有许可证声明。v1.1.1 查明 Apache-2.0 是补录用的 twang2218 数据集的许可证，被错当成了主数据集的。
- 教训：数据管道取数时只认标题、不认版本。数据集明明带着"状态"和"施行日期"字段，补录时却没有用上；固定版本加逐文件哈希，就是为了让这类错误在评测之前暴露出来。

**改动。**

- 只用公开数据集一个固定 revision 的 236 个原始文件。仓库提交逐文件 SHA-256 清单，提供 `fetch-corpus` 和 `verify-corpus`；审计时语料与清单不一致就拒绝运行。
- 解析器补上"第X条之Y"（刑法中 53 条），否则它们会和第X条撞号。
- 证据检查改为按规范化条号比对。修之前，检索已经能找到"第二百六十四条"，证据检查却仍然判"缺少第264条"，问答链路可能因此拒答。

详见 [v1.0.0 基线报告](retrieval/V1_0_BASELINE.md)。

## 5. 第四层：评测集本身只是开发集

v3 全部由大模型生成，又被反复用来做设计决策（切分策略、embedding 选型、adaptive 是否默认开启），没有留出集。处理方式：

- v3 在冻结语料上逐条复核，得到开发集 `legal-eval-dev-v1`：删掉 7 条（6 条的法律不在语料中，1 条的题目前提来自旧版公司法），其余一字不改，由注册表校验与父集逐条相同。
- 所有数字都按开发集数字报告；历史结论（如 Qwen3 0.981）标明是旧语料、修复前解析器上的结果。
- 没有当场再造一套"留出集"：再让大模型生成一套题，问题还是同一个。真正的留出集需要人工撰写，并且冻结后只用一次。

## 6. v1.0.0 基线（冻结语料，BM25，开发集）

| 题集 | 条数 | Hit@1 | Hit@5 | Hit@20 |
| --- | ---: | ---: | ---: | ---: |
| 开发集（有标准答案） | 101 | 0.614 | 0.723 [0.634, 0.802] | 0.802 |
| 其中带条号的查询 | 24 | | 1.000 | 1.000 |
| 其中生活化描述 | 27 | | 0.444 | 0.556 |
| 合成条号集 | 708 | 1.000 | 1.000 | 1.000 |

同样的 101 道题，换成冻结语料后 Hit@5 从 0.703 变为 0.723。这个差异来自语料（多了 31 部法律，4 部法律带编者条旨），并且落在置信区间内，所以不算效果提升。

### v1.1.0：同一份语料上的向量检索、多路召回与重排

v1.0.0 只测了 BM25。v1.1.0 把模型调用改走 SiliconFlow API（[项目边界](../docs/PROJECT_SCOPE.md) D8），在同一份语料和同一套题上把各个组件各测一次、不调参，完整表格见 [v1.1.0 设计消融](retrieval/V1_1_SILICONFLOW.md)：

| 方法 | 开发集 Hit@5 | 生活化描述 Hit@5 | 条号集 Hit@1 |
| --- | ---: | ---: | ---: |
| BM25 | 0.723 | 0.444 | 1.000 |
| bge-m3 向量 | 0.921 | 0.815 | 0.267 |
| Qwen3-Embedding-4B 向量 | 0.980 | 0.926 | 0.174 |
| BM25 + bge-m3 多路召回（RRF） | 0.842 | 0.667 | 0.668 |
| BM25 + Qwen3 多路召回（RRF） | 0.901 | 0.778 | 0.760 |
| BM25 + 重排 | 0.772 | 0.519 | 0.939 |

- 向量检索比 BM25 高 19.8 到 25.7 个点（配对 bootstrap 区间不跨 0），提升几乎全部来自生活化描述。
- 多路召回比向量单路低 7.9 个点，两个向量模型都是，区间 -13.9 到 -2.0。RRF 只看排名，弱的一路排在前面的错误结果被拉进了前 5。
- 向量检索在精确条号上很差。把法律名和条号拼进向量文本能补一大截，bge-m3 从 0.267 提到 0.452，Qwen3 从 0.174 提到 0.775，但仍低于精确查表的 1.000；开发集上这项文本工程没有显著影响。
- 重排没有显著收益：在 BM25 上多出的 5 个点区间跨 0；在最强的 Qwen3 向量上反而降了 5.9 个点（区间 -10.9 到 -2.0），Hit@1 从 0.891 掉到 0.673。加重排后所有组合的 Hit@1 都落在 0.64 到 0.67，说明前几名由重排模型决定，而它在这批题上不如 Qwen3 向量本身。重排还把条号查询排第一的比例从 1.000 拉到 0.939。
- 由此提出按查询类型路由：解析出（法律，条号）的走精确查表，其余走向量。事后模拟两头都是最好（开发集与向量单路相同，条号集 1.000），但这条规则是看了开发集结果才提出的，所以没有改默认。
- Qwen3 的 0.980 和旧语料上的 0.981 几乎相同：那个数字没有被数据问题抬高，但它仍是开发集数字。

## 7. 负结果（保留，不删）

这些结论来自 2026-06 的旧语料和修复前的解析器，方向可参考，具体数字不能和第 6 节直接比较：

- **规则式查询改写（adaptive）有害**：BM25 Hit@5 0.704 -> 0.667，P95 延迟约为直接检索的 3.8 倍。改写丢掉了关键词，所以默认关闭。
- **RRF 不是免费的午餐**：Qwen3 向量检索单路 0.981，与 BM25 融合后反而降到 0.944。两路质量接近时融合才有收益（bge：0.704 和 0.676 融合后 0.796）。v1.1.0 在冻结语料上复现了这一点：两种向量模型与 BM25 融合后，都比向量单路低 7.9 个点（见第 6 节）。
- **法律领域专用 embedding 最差**：ChatLaw-Text2Vec 只有 0.222，"领域模型一定更好"不成立。
- **框架默认 BM25 不能直接用**：LlamaIndex 默认 BM25 不处理中文分词，只有 0.111。
- **换成熟中文分词没有带来确定收益**：草稿 PR #31 对照了 SmartCN、Elasticsearch IK 等分词，提交记录自述为负结果或"默认取舍未解决"，该 PR 关闭不合并。

## 8. 代价与取舍

- **精力花错了地方。** 服务化（PostgreSQL 版本化快照、FastAPI、LangGraph checkpoint、Celery 批任务、观测）做得很完整，但核心检索的解析 bug 存在了几个月都没被发现，因为度量只看"条号对没对上"。先度量数据，再度量模型。
- **治理比代码重。** 每个里程碑都有状态文件、发布回执和交接文档，维护成本一度超过功能本身。v1.0.0 起只保留"分支 -> PR -> CI -> 合并"。
- **范围冻结。** 检索重构止于 R2，界面不做，草稿 PR #31 不合并。完整决定见 [项目边界](../docs/PROJECT_SCOPE.md)。

## 9. 尚未解决

见 [项目边界](../docs/PROJECT_SCOPE.md) 第 5 节。最重要的三条：没有留出集；按查询类型路由只是事后模拟，还没有做成检索选项，也没有在独立的题上验证；服务层不接受说不清版本的 API 向量，所以线上路径仍只有 BM25。

## 10. 设计取舍问答

**为什么自研 BM25，而不是用框架或搜索引擎？**
框架默认 BM25 不处理中文（0.111）。法律检索需要单字、双字、书名号标题、条号这几类特征，还需要逐条的 ranking trace 来解释排名。PR #31 对照过成熟分词，没有得到确定收益。

**为什么按"条"切分？**
原始数据就是一行一条；条号引用、来源展示和证据检查都依赖条文粒度。按窗口或固定字数切分的 Hit@5 差异落在置信区间内，没有理由放弃条文边界。

**为什么法律名必须精确匹配？**
子串匹配会让"保险法"命中"社会保险法"。别名表从语料标题生成，最长匹配优先，书名号里只认完整标题。

**精确命中为什么用一个很大的加分常数，而不是单独一条通道？**
这是改动面最小的过渡方案：服务路径和实验路径都直接构造 `BM25Retriever`，在它内部置顶，两条路径同时生效，返回结构不变。代价是分数语义混在一起，而且 RRF 和重排序不保证维持置顶；这已记为局限。

**Qwen3 的 0.981 可信吗？**
v1.1.0 在冻结语料、修复后的解析器上重测为 0.980 [0.951, 1.000]，和历史数字几乎相同，说明它没有被数据问题抬高。但它仍是开发集数字：评测题由大模型生成、被反复使用，没有留出集，不能当成泛化能力。

**为什么不用混合检索（多路召回）？**
测过。两种向量模型和 BM25 用 RRF 融合以后，都比向量单路低 7.9 个点，条号查询排第一的比例也只有 0.67 到 0.76。两路质量差太多时，融合会把弱的一路的错误结果拉进来。向量擅长大白话，BM25 精确查表擅长条号，所以更合理的是按查询类型路由，而不是一刀切地融合。

**怎么防止过拟合？**
先承认：没有留出集，设计选择都是在开发集上做的，所以数字偏乐观。能说清楚的是：BM25 参数没有在评测集上搜索过：k1、b 用的是常见默认值，法律名和条号的加分常数在仓库第一次提交里就写死了，早于 v3 评测集，仓库里也没有任何调参记录。下一步是人工撰写一套冻结后只用一次的留出集。

**为什么换语料后分数反而高了？**
语料不同：多了 31 部法律，劳动合同法等 4 部法律带编者条旨，IDF 统计也变了。差异在置信区间内，所以不报告为提升。

**如果继续做，第一件事是什么？**
人工写 50 到 100 道不看条文的生活化问题作为留出集，冻结后只用来评估一次。有了它，路由、重排和补充检索这些现在只能在开发集上看的取舍，才有可信的依据。
