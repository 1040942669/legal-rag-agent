## 核心机制与不变量

### 1. 身份、所有权与非枚举访问

- 客户端只提交 opaque Bearer credential。服务端把它映射为固定的 `(user_id, scope_id, profile_id)` principal，客户端不能从 URL、query 或 body 覆盖这些身份字段。
- session、run、event、result、cancel 和 resume 的读取或状态变更都同时限定已鉴权 `user_id`。资源不存在和资源属于其他用户使用相同的 not-found 语义，避免通过状态码或错误细节枚举他人资源。
- M4 的 `resume` endpoint 先执行相同的 ownership 检查，确认资源归属后才明确返回 `resume_not_supported_until_m5`。它不会以“尚未实现”为由跳过授权边界。

### 2. 短事务、幂等与一个 active run

- 创建 run 时锁定 owner-scoped session row，在同一短事务中先处理 idempotency，再检查 active-run 约束，并原子写入 queued run、一条 user message、idempotency binding 和 `run.queued` 事件。
- idempotency key 以 `(user_id, session_id, idempotency_key)` 为作用域，绑定 canonical request hash 和一个有限 TTL。同 key + 同 canonical body 返回既有 run；同 key + 不同 body 返回 409；过期 key 只能在 serialized session transaction 内清理后复用。
- 应用层 active check 用于返回可归因错误，最终正确性由 PostgreSQL partial unique index `uq_runs_one_active_per_session` 保证。该索引覆盖 `queued`、`running`、`interrupted`，因此两个并发不同 key 不能都创建 active run。
- `interrupted` 在 M4 仍占据 active slot。owner 必须先取消，再创建 replacement run；系统不会把 interrupted 隐式当成可重跑或已经完成。
- 检索、生成、验证和 provider 调用都发生在数据库事务之外。数据库事务只保护可持久化的状态跃迁，避免把外部调用延迟变成 row lock 或连接池占用时间。

### 3. 接收时冻结完整执行边界

- run 接收时锁定并验证 active snapshot pointer 和 validated embedding import，然后持久化 authenticated user/scope、`snapshot_id`、activation `revision`、`activation_id`、`profile_id`、typed retrieval boundary fingerprint、retrieval config hash、graph version、canonical request payload 和 request hash。
- worker 只加载该 frozen input 与来自 succeeded runs 的有界历史。后续 snapshot activate/replace/rollback 不会把已排队的 run 重定向到另一个 corpus 或 profile。
- history 同时受消息数和字符数限制；draft、failed、cancelled、interrupted 或没有 durable result 的 turn 不会伪装成可供下一轮使用的成功历史。
- run 与 result 的公开读取使用单一一致性读取路径，不先读 terminal status 再在另一个事务中猜测 result 是否存在。

### 4. Claim、租约、CAS 与晚到结果 fencing

- supervisor 是有界单进程执行器。claim 使用 `FOR UPDATE SKIP LOCKED` 在短事务中取得 queued run，分配 `lease_owner` 与有限 `lease_expires_at`，并推进 run revision 和 event sequence。
- stage event、heartbeat/状态推进和 terminal publish 都重新锁定 run，并验证 owner、旧 revision、旧 event sequence、lease 和当前状态。cancel、stale recovery 或其他 terminal transition 先成功后，旧 worker 即使仍在执行也不能发布。
- lease 有效性使用 PostgreSQL `clock_timestamp()`。事务级 `now()` 固定在事务开始时间，若 worker 在 row lock 上等待，可能在真实 lease 已过期后仍被旧时间错误授权；M4 的真实 PostgreSQL 回归明确覆盖这一点。
- timeout 或 shutdown 发生时，callback delivery token 立即失效，仍未退出的线程进入 bounded quarantine。晚到 callback 同时受进程内 token 和数据库 lease/revision fence 两层拒绝。
- quarantine 达到上限后不再 claim 新工作，readiness 失败关闭。`stop()` 在 supervisor loop、active execution 或 quarantined execution 尚存时返回 false；FastAPI lifespan 仅在 complete stop 后 dispose SQLAlchemy engine，避免 draining thread 访问已销毁依赖。

### 5. SSE 是持久事件回放，不是第二次执行

- 每个 `run_events` 记录由 PostgreSQL 分配并保存单调 sequence；SSE `id` 即该 sequence。客户端可用 `Last-Event-ID` 或经校验的 `after` cursor 重新鉴权并补读严格有序后缀。
- SSE disconnect 不取消 run，也不会创建新 run。客户端重连只读取数据库事件源，幂等绑定和 execution identity 都保持不变。
- stream 不会仅因为 run status 已 terminal 就立即关闭。若 terminal transition 与一次空 event poll 竞争，stream 会比较 durable `event_sequence`、重新读取并发送缺失的 terminal event，然后才结束。
- event type 和 payload 使用 closed allowlist，只允许 bounded count、稳定 stage/status/reason 等安全字段，不持久化 raw prompt、credential、任意 exception、模型草稿或未验证 answer。

### 6. 验证后发布与拒绝草稿隔离

- generator draft 是 executor 私有中间态。只有安全 verification payload 明确 `passed=true` 后，系统才允许构造公开 result。
- success publication 在一个事务中写入 safe `run_results`、final assistant message、`answer.final` event、run terminal status、revision 和 event sequence。因此客户端不会看到没有对应 durable result 的 terminal success，也不会看到 result 已存在但 final event 尚未提交的中间态。
- verification 拒绝的 pre-fallback draft 不会进入 HTTP response、SSE payload、`messages`、`run_results`、`run_events` 或正常日志诊断。M4-T06 从 HTTP、SSE、数据库和 executor 四个方向复验这一闭包。

### 7. 重启恢复是状态分类，不是假恢复

- supervisor 启动和周期扫描会分批 drain 所有 lease 已过期的 `running` rows，将其原子转换为 `interrupted` 并附加 durable terminal event，然后才 claim 新工作。
- `queued` 仍可由新 supervisor claim；已完成 history/result 继续可读；非过期 lease 不会被启动过程武断打断。
- M4 不重建外部 provider 调用、节点局部内存或未持久化 side effect，也不自动 retry。`resume` 明确返回 501 语义，直到 M5 建立 checkpoint 和 side-effect-aware resume contract。
- 真实 PostgreSQL service stop/start 与独立 application process restart 是两种不同证据。前者证明数据库 schema、M3 corpus/activation/exact/catalog/ANN receipt 与 M4 migration 在服务重启后仍可核验；后者证明 API 进程更换后 history/result 仍在，expired running 被分类为 interrupted，cancel 后能启动 replacement run。

### 8. 可选 service、真实 PostgreSQL 接线与零付费调用

- FastAPI、Uvicorn、SQLAlchemy、Alembic、psycopg 和 pgvector 保持在可选 `service` dependency group。`legal-rag-api` 延迟 import service 栈；原 `legal-rag` CLI 不因 M4 被迫依赖 API 或数据库运行环境。
- M4 的 service wiring 使用真实 PostgreSQL frozen corpus 和既有 typed retrieval boundary，但 executor 配置为 `generate=False`。这验证生产接线路径、持久化和安全状态机，不伪装成 live-model 质量验证。
- 本候选调用真实或付费 generation model、remote embedding、reranker、LLM judge 的次数为 `0`，也没有未经预算授权的模型调用。

## 验收结果

### 首轮累计门禁的真实负结果与修复

M4 累计门禁第一次执行没有通过，不能把它省略或并入最终绿灯。失败包括两类：

1. startup recovery 参数契约不一致。`RunSupervisor._recover_all_stale_runs` 调用了 `recover_stale_runs(limit=...)`，而真实 `RunService` 接口使用 `batch_limit`。这会在真实 service startup recovery 路径触发错误并影响 readiness。修复统一了调用参数和测试 fake 的签名，重新执行真实启动与累计门禁后通过。
2. quarantine shutdown timing 断言与加固后的生命周期语义不一致。实现增加共享的 0.1 秒 bounded drain grace；短时间内已经释放的 quarantine thread 可被收束，真正仍阻塞的 execution 则让 `stop()` 返回 false，且 lifespan 不 dispose engine。测试随后按这一 fail-closed 语义等待和断言，复验 late callback fencing 与后续 run 不受污染。

以上问题均在最终本地证据之前修复并重新执行相关测试。没有把失败 run 改写为 passed，也没有用跳过测试、放宽数据库不变量或关闭 shutdown fencing 来获得绿灯。
