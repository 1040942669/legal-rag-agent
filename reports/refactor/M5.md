## 核心机制与不变量

### 1. 一个图控制循环，而不是两层 Agent loop

M5 的固定图版本为 `m5-bounded-v1`：

```text
analyze_query
  -> route
  -> retrieve
  -> merge_evidence
  -> check_evidence
  -> [plan_followup -> retrieve]  # 仅在预算和证据条件允许时
  -> generate
  -> verify
  -> persist_result
```

- 图是唯一自适应控制器。旧 assistant 的 `adaptive_enabled`、`adaptive_use_llm` 和未记账的查询压缩不能与图循环叠加。
- follow-up 检索次数、每轮 query 数、工具调用、模型调用、embedding 调用、单操作重试和绝对 deadline 都有硬上限。
- 默认上限为：2 个检索轮次、每轮 3 个 query、8 次工具、4 次模型、4 次 embedding、每个外部操作 1 次重试、90 秒绝对 deadline、`top_k=5`。
- 达到限制时返回可持久化 `stop_reason`；系统不会为了追求答案而无限循环。

### 2. Checkpoint state 是关闭的 JSON 合同

- state schema version 为 `1`，graph version 为 `m5-bounded-v1`。
- state 使用精确字段集合，只接受 JSON 可表示值，拒绝 `NaN`、`Infinity`、未知字段和递归敏感字段。
- prompt、secret、credential、raw draft、数据库连接、HTTP client 等对象不能进入 checkpoint。`answer_draft_ref` 在当前合同中必须保持 `null`。
- `run_id`、session、user、scope、snapshot、profile、graph identity、budget limits 和 absolute deadline 在节点执行期间不可被节点修改。
- state 被包装在 LangGraph 的 `payload` channel 内，避免与 framework 保留的 `checkpoint_id` 名称冲突。

### 3. PostgreSQL checkpoint 与业务投影各司其职

- 可恢复运行只允许 `PostgresSaver`。`InMemorySaver` 即使能完成同进程演示，也会被配置和验收显式拒绝。
- serializer 使用禁止 pickle fallback 的严格 `JsonPlusSerializer`，防止任意 Python 对象或可执行序列化形式进入持久 checkpoint。
- LangGraph 管理自己的 checkpoint 私有表；应用侧 `run_checkpoints` 只保存经过校验的业务投影、hash、schema/graph version、最后完成节点和 lease epoch。
- 每次 claim/resume 使用隔离的 framework thread identity。LangGraph 根 namespace 当前为空，因此应用 namespace 单独保留在业务投影中。
- resume 只信任 run row 指向的应用 checkpoint。旧 lease 在旧 namespace 留下的孤儿 framework checkpoint 不能推进业务 pointer。

### 4. 预算先预留，崩溃后不退款

- `run_budget_ledgers` 是所有恢复进程共享的 durable counter，不从 checkpoint 内的临时计数猜测余额。
- 每次外部操作在 dispatch 前先原子预留预算，attempt 再经历 `reserved`、`dispatched`、`succeeded`、`failed`、`outcome_unknown` 或 `abandoned_before_dispatch`。
- 进程在 `reserved` 后、dispatch 前停止，可恢复为 `abandoned_before_dispatch`；已经 `dispatched` 则保守地记为 `outcome_unknown`。
- 已成功返回但结果没有严格早于最新可信业务 checkpoint 时，也保守改判为 `provider_result_not_durable` 的 unknown。时间相等不被当作已持久化证明。
- 429 和 timeout 只在配置预算内有限重试；400 和 401 不盲重试。

### 5. 显式恢复、绝对 deadline 和未知外部结果

- `interrupted` 不会自动重新执行。owner 必须显式调用 resume；重复 resume 请求保持幂等。
- resume 先验证 checkpoint 的 schema、graph、identity、hash 和业务 pointer，再把 run 变为可领取。验证失败不移动 checkpoint，也不设置恢复请求。
- resume 不重置 absolute deadline 或任何 durable budget。deadline 已到时不得再发起外部调用，并以 `completed_with_limits` 和对应 stop reason 结束。
- claim 会增加 `lease_epoch`，worker heartbeat 只续租同一 epoch。旧 owner 不能写 checkpoint、stage event 或终态。
- 默认不重试 outcome unknown 的外部调用，避免静默复制 provider/planner 请求。此机制披露可能重复费用，但不声称 exactly-once。

### 6. 三类崩溃窗口使用不同恢复规则

1. 检索 checkpoint 已保存、生成尚未开始：resume 重用已保存的检索证据，不再重复整个检索阶段。
2. provider 或 planner 已 dispatch，甚至已经返回，但结果还未进入可信 checkpoint：attempt 记为 `outcome_unknown`，预算不退回，默认不静默重发。
3. immutable result、assistant message 和 final event 已在同一事务提交，但图的最后 checkpoint 未写完：恢复时以唯一 durable result 对账，不生成第二个答案。

### 7. 澄清追问是新 run，不是覆盖父 run

- `needs_clarification` 是 answer-bearing terminal status。
- 用户补充信息时，在同一 session 创建新 run，并可提供 `parent_run_id`。
- 父 run 必须属于同一 owner 和 session，且处于允许的 answer-bearing terminal status。
- 无 parent 的普通请求保持 M4 canonical request hash 兼容；有 parent 的请求 hash 同时绑定 request 与 parent identity，避免同一 idempotency key 跨 lineage 误复用。
- child run 有独立 deadline 和 budget ledger，history 可读取安全父结果，但不会修改父 run 已消耗的额度。

### 8. 数据库 fencing 是最终写权限

- `lease_owner`、`lease_epoch`、数据库 wall clock、run revision 和 event sequence 共同决定写权限。
- checkpoint pointer、stage event、attempt 对账和 terminal publish 都重新验证当前 epoch。
- 两个进程竞争同一 run 时至多一个 owner 有效；失效 owner 的 checkpoint 和 terminal write 都被拒绝。
- immutable terminal publication 后允许同一 epoch 补写 graph final checkpoint，用于完成框架状态收口；其他 epoch 仍被 fence。

### 9. 工具和 prompt injection 边界

模型可见的只读工具固定为：

- `search_laws`
- `get_article`
- `get_neighbors`
- `inspect_evidence_metadata`

客户端、证据文本和模型输出都不能覆盖 authenticated scope、snapshot、profile、user、数据库 DSN 或 SQL。把工具指令、密钥索取或范围变更文字嵌入证据，只会作为不可信内容处理，不能增加工具、改变冻结过滤范围或把 prompt/secret 暴露到 result、event、checkpoint 和普通日志。

### 10. 兼容 M4 和 provider-free 默认路径

- 非 M5 graph version 继续走 `LegalChatRunExecutor`，不被强制迁移到新图。
- `/resume` 只对 M5 graph version 的合法 `interrupted` run 启用；旧 M4 run 保持明确 unsupported 语义。
- `legal-rag-api --migrate` 先运行 Alembic，再初始化 LangGraph PostgreSQL saver schema；普通启动会验证 checkpointer readiness，不隐式迁移。
- 默认 `GraphRunExecutor(generate=False)` 不调用 live model。候选验证的真实/付费 generation、remote embedding、reranker 和 LLM Judge 调用均为 `0`。

## 安全与成本口径

- 候选测试显式设置 `ALLOW_LIVE_MODEL_CALLS=false`，不读取 `.env`，不调用真实或付费模型。
- generation model、remote embedding、reranker、LLM Judge 调用数均为 `0`。
- fault receipt 使用关闭字段 schema、大小/深度限制、敏感字段名和值扫描，并要求 candidate SHA 与 checked-out HEAD 精确一致。
- 预算预留发生在外部 dispatch 之前。崩溃后不退款是一项保守成本规则，不是 provider 请求 exactly-once。
- prompt injection 测试证明的是工具、范围和披露边界，不证明模型回答的法律正确性。
- 测试只使用 loopback PostgreSQL 与合成输入，不上传私密语料、token、数据库 URL 或本地数据。

## 已知限制

- LangGraph 提供控制流和 checkpoint 协议，不自动提供业务事务或外部 side-effect exactly-once。
- PostgreSQL saver 与业务 checkpoint pointer 之间没有跨两套表的单一原子事务，所以恢复只信任应用投影，并对不确定 provider 结果失败关闭。
- 默认 unknown external outcome 不自动重试，可能以 `completed_with_limits` 结束；这是避免静默重复费用的设计，不是高可用吞吐策略。
- supervisor 仍不是通用分布式队列。M6 才处理批量评测和语料/索引导入的任务队列、可观测性和 worker 运营。
- `needs_clarification` 后的用户补充是新 run，不能把旧 run 的 deadline 或额度重置后继续使用。
- downgrade 不是 valued M5 数据的安全回滚工具。若已有 M5-only terminal status/event，迁移会先拒绝；即使允许，删除 M5 表/列仍会丢失恢复和审计数据。
- 当前结果不证明完整现行法律覆盖、语义蕴含、个案法律结论、live-model 质量、生产容量或灾难恢复能力。

## 回滚和兼容策略

- 代码回滚使用新的 revert/fix PR，不强推、不改写共享历史、不移动既有 release Tag。
- 新 run 可以通过 graph version 选择稳定的 legacy executor；已有 M5 run 必须由兼容 runner 恢复、明确终止或经过显式迁移，不能忽略 checkpoint version 强行继续。
- M4 的无 parent request hash 保持兼容；parent-bound follow-up 使用新的 lineage-aware hash，不能相互冒充幂等 replay。
- 若 M5 PostgreSQL checkpointer 不可用，readiness 失败关闭；不能静默降级到 `InMemorySaver`。
- 若外部结果不确定，保留 attempt 和已消耗预算，向客户端返回明确限制原因。不能为了“看起来成功”而清账重跑。
- 数据库 schema 需要回退时优先前向修复或经过备份的迁移计划，不直接对有价值运行历史执行破坏性 downgrade。
