## 验收结论

M5 达到了 MASTER_PLAN 的工程验收目标：M4 中只能持久记录、不能节点级继续的 `interrupted` run，现已具备 PostgreSQL 持久 checkpoint、显式 resume、durable budget、absolute deadline、external attempt journal、lease epoch fencing、兼容性失败关闭和跨进程 hard-kill 恢复。M5-T01 至 M5-T10 在精确软件候选和 release target 上全部通过。

本结论只覆盖 provider-free 工程正确性和已列明的故障窗口，不覆盖外部 provider exactly-once、真实法律正确性、生产容量、完整现行法律覆盖、live-model 质量或成本。

## 运行与恢复机制

### 单一有界图

固定 graph version 为 `m5-bounded-v1`：

```text
analyze_query
  -> route
  -> retrieve
  -> merge_evidence
  -> check_evidence
       -> plan_followup -> retrieve  # 仅在证据不足且预算仍允许时
       -> generate
  -> verify
  -> persist_result
```

默认限制为 2 个检索轮次、每轮 3 个 query、8 次工具、4 次模型、4 次 embedding、单操作 1 次重试、90 秒绝对 deadline 和 `top_k=5`。旧 adaptive/planner loop 不与此控制图叠加。

### 双层 checkpoint 与可信 pointer

LangGraph saver 保存框架 channel 和 checkpoint；应用侧 `run_checkpoints` 保存经过验证的业务投影、hash、graph/schema version、最后完成节点、application namespace 和 lease epoch。resume 只信任 run row 指向的应用 pointer，旧 epoch 留下的孤儿 framework checkpoint 无权推进业务状态。

### 预算与 side effect

外部动作在 dispatch 前先预留预算并落 attempt：

```text
reserved -> dispatched -> succeeded | failed | outcome_unknown
    -> abandoned_before_dispatch
```

已 dispatch 的调用在恢复时如果无法证明结果进入可信 checkpoint，就记为 `outcome_unknown`。预算不退款，默认不重复 provider/planner 调用，并保存 `possible_duplicate_cost=true`。这是一条保守成本和一致性规则，不是 provider exactly-once 保证。

### lease 与终态发布

claim/resume 递增 `lease_epoch`。heartbeat、budget、attempt、checkpoint、event、result 和 terminal transition 都验证当前 owner、epoch、revision 与数据库时间。最终 result、assistant message 与 final event 在同一数据库事务发布；如果进程在此后、图末 checkpoint 之前停止，恢复只对账已有唯一结果。

### clarification lineage

`needs_clarification` 是父 run 的 answer-bearing 终态。补充信息产生同 session 的新 run，并以 `parent_run_id` 绑定 lineage；child 拥有独立预算和 deadline，父预算不变。parent identity 进入幂等 hash，旧 M4 无 parent 的 hash 公式保持兼容。

## 保留的失败与修复

### 较早 PR run 的 M4 readiness 回归

`7ba6ae8...` 的 [run 36495569685](https://github.com/1040942669/legal-rag-agent/actions/runs/36495569685) 在 M4 service job 得到 `78 passed, 1 failed`。失败测试是：

`integration_tests/test_m4_process_restart.py::test_m4_t04_independent_process_restart_preserves_history_and_interrupts_stale_run`

原因是 M5 production readiness 正确要求 persistent PostgreSQL checkpointer，但遗留 M4 deterministic process fixture 没有建立该 checkpointer。`aaa5613` 把该旧 fixture 明确固定为 `m4-linear-v1`，保持生产 M5 fail-closed 语义；`979c12f` 只做格式化。目标测试随后 `1 passed in 10.82s`，最终 PR 和 master 三路 CI 都成功。

- 第二次 fresh database 完成真实 restart，但数据库名不满足 integration guard 前缀。
- 第一次累计 gate 因同一 guard 问题在 fixture setup 失败关闭。
- 使用 `legal_rag_m3_test_m5_aa737e8` 新库后，migration 0001 至 0006、prepare、真实 PostgreSQL stop/start、new-process verify 和 51/51 gate 全部通过。

这些失败没有被删除或冒充成功；只有 guard-compliant fresh rerun 和对应精确 SHA 被用作发布证据。

## 安全与成本口径

- 所有发布测试均禁止 live model call，不读取或上传真实凭证、问题正文、证据正文或数据库 URL。
- generation、remote embedding、reranker 与 LLM Judge 真实调用数为 0。
- fault receipt 使用关闭 schema、重复 key 拒绝、大小/深度限制、敏感字段和值扫描，并强制 candidate SHA 等于 checked-out HEAD。
- 工具测试证明 allowlist、冻结 scope 与数据披露边界，不证明模型回答的法律正确性。
- 仓库没有 branch protection 或 ruleset，但执行过程中仍主动要求 exact-head PR CI、普通 merge、exact merge-target master CI；没有使用 `--admin`、auto-merge、squash、rebase 或强推。

## 已知限制与提升方向

- 外部 provider exactly-once 无法由 checkpoint 保证。后续优先适配 provider idempotency key、账单对账与 unknown outcome 运维处理。
- LangGraph saver 与应用投影不是一个跨表全局事务。当前使用可信 pointer、lease epoch 与失败关闭；可进一步研究 outbox 或提交协议。
- 当前 supervisor 不是分布式队列、多 worker 公平调度或高吞吐执行平台；M6 尚未开始。
- wheel 在不同 CI job 中大小相同但 SHA 不同，说明构建未 byte-for-byte reproducible；应固定 ZIP timestamp 与构建元数据。
- checkpoint retention、归档、租约回收、budget/attempt 指标、告警和恢复演练尚未达到生产 SLO。
- 静态 bearer token、loopback fixture 和 provider-free fake 不是生产 IdP、TLS、rate limit、容量、灾备或合规验证。
- 当前证据不证明完整现行法律覆盖、引用语义蕴含、个案法律结论、live-model 质量、成本或 P95/P99 延迟。
- Alembic `0006` downgrade 会删除 M5 checkpoint projection、budget、attempt 和 artifact 数据，不应对有价值历史盲目执行。
- GitHub Actions 对 pinned `actions/upload-artifact` 给出 Node.js 20 deprecated、强制 Node.js 24 的非阻塞警告，后续应升级 action pin。

## 回滚与兼容

- 代码回滚使用新的 revert/fix PR，不强推、不重写共享历史、不移动 `v0.6.0`。
- 新 run 可通过 graph version 选择 legacy executor；已有 M5 run 必须由兼容 runner 恢复、明确终止或显式迁移。
- M4 无 parent request hash 保持兼容；parent-linked follow-up 使用 lineage-aware hash。
- PostgreSQL checkpointer 不可用时 readiness 失败关闭，不回退 `InMemorySaver`。
- schema 回退优先使用前向修复或经过备份和批准的迁移计划。
