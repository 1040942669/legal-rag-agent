## 模块 B 核心语义

### exact score 与稳定排序

- PostgreSQL 使用 pgvector `<#>` operator。该 operator 返回 negative inner product distance，repository 显式计算 `score = -distance`，输出统一的越大越好 inner-product score，并把 `-0.0` 规范为 `0.0`。
- SQL 首先按 distance 升序，再按 `snapshot_ordinal` 和 `chunk_id` 升序，确保完全并列分数具有稳定次序。RRF、adaptive merge 和 reranker 也使用确定性的次级排序键。
- 同一个 query vector、snapshot、profile 与候选集合下，pgvector exact 的 chunk 顺序和 score 与 NumPy dense 基线在明确浮点容限内一致。

### hard filter 必须先于 `LIMIT`

- 强制边界包含 `scope_id`、`snapshot_id`、`profile_id`，以及可选的 `law_ids`、`version_ids`、`article_ids`、`article_numbers` 和 `[valid_from, valid_to)` `effective_on`。
- exact SQL 在排序和 `LIMIT` 前同时限制 scope、serviceable snapshot、validated import receipt、profile 和法条关系；不会先取全局 top-k 再做应用层过滤。
- BM25 不在全量 corpus 上检索后补过滤，而是先从 PostgreSQL 加载同一个 bounded corpus，再由 `BoundaryBoundRetriever` 绑定完整边界。
- 多 article chunk 采用严格披露语义：至少有一条关系命中且不存在任何违反完整组合 selector 的关系。只要其中一个关联法条越界，整个 chunk 都不会返回，避免混合 chunk 暴露非匹配文本。
- 空 selector tuple 是显式 deny-all；非法 ID、重复 selector、非法日期、非法 `top_k` 和非有限向量在距离查询前失败关闭。

### typed provenance 与下游闭包

- 每个 bound result 携带 `RetrievalProvenance`，包含完整 boundary、scope/snapshot/profile、chunk ID、chunk content hash、重新水合后的 payload hash、snapshot ordinal、embedding hash 和有序 article provenance。
- 数据库关系是 law/version/article metadata 的权威来源。读取时重算持久化 chunk payload 和 float32 vector hash，检测 text/metadata/vector 漂移；migration `0002` 同时阻止受保护行的 update/delete 以及 validated snapshot 的成员追加。
- RRF 要求 lexical/dense 两个叶子同时 unbound，或共享完全相同的 typed boundary；只比较 trace fingerprint 不足以获得信任。融合、adaptive direct/multi-plan/follow-up、rerank、chat staging/generation/verification 均重新校验 provenance。
- 同一 `chunk_id` 若从不同路径带回不同 chunk payload 或 provenance，会直接拒绝，不按分数静默覆盖。chat 在任何 completion 调用前再次核对捕获边界，并对 evidence 做 defensive copy。
- artifact 在保留 M2 unbound 格式和既有 hash chain 可读性的同时，为 bound result 保存完整 typed boundary/provenance；伪造 trace、缺 provenance 或 compatibility metadata 不一致均不能绕过检查。

### query profile 与不可变模型 revision

- retrieval 构造时先核对 snapshot 是否 serviceable、profile 完整 identity 是否与 encoder 相同、snapshot/profile import receipt 是否为 `validated`；构造失败时 encoder 调用数为 0。
- query vector 必须是有限、精确维度的 canonical float32；normalized profile 还要求非零且 L2 norm 在容限内。profile、维度、normalization 或 adapter contract 不一致均在执行相似度查询前报错。
- 在线 version-bound encoder 只接受可核验的 `sentence_transformers` Hub `owner/model` 与 40 位小写 commit SHA revision，不接受本地 repository-shaped 路径，也不允许 `trust_remote_code=True`。当前 SiliconFlow adapter 无法证明不可变 revision，因此不能用于 version-bound query encoder。

## 模块 C 核心语义

### 精确法条目录与显式失败状态

- `ArticleLookupRequest` 使用不含 embedding profile 的独立 boundary：已鉴权调用方固定 `scope_id`、`snapshot_id` 和可选 law/version/article allowlist，查询只依赖关系键和 snapshot membership，不把向量 profile 强加给结构化法条读取。
- 查询键是精确法名与规范化条号，并可选固定 `law_id`、`version_id` 和/或 `effective_on`。SQL 不做模糊标题、语义召回或跨版本 fallback；显式版本不存在或在请求日期不生效时返回 `not_found`，不会换成相邻版本或相邻条文。
- 结果严格分为 `found / not_found / needs_disambiguation`。同名但不同法律身份、无日期的多个精确版本、已核验有效期重叠，以及未知/未核验有效期分别有稳定 reason；候选只披露版本元数据，不携带多个正文。
- 日期统一采用半开区间 `[valid_from, valid_to)`。该条件只证明检索版本元数据覆盖请求日期，不自动判断具体案件应适用的法律版本。
- found 正文来自权威 `law_articles` 行。查询通过 `article → chunk relation → snapshot chunk` 证明成员关系，并重算 article/chunk payload hash；多文章或重复分块只形成有序 membership proof，不拼接混合 chunk 正文。request、boundary、version metadata、article payload 和 membership 均有可重算 fingerprint/hash。

### revisioned active pointer 与原子切换

- active pointer 同时保存 snapshot、单调 revision 与 activation ID，并引用不可变 activation event。event 保存 operation、前一 snapshot/event、目标 snapshot、actor/reason 和事务时间；数据库延迟约束在提交时核对 active 状态、pointer、最新 event 和前驱链。
- activate/replace/rollback 先取得 scope 级 transaction advisory lock，再锁定 pointer 与按 ID 排序的目标/当前 snapshot 行，并对调用方给出的完整 `(snapshot_id, revision, activation_id)` 执行 CAS。同 scope 并发竞争恰好一个事务提交，失败者不留下部分 event、状态或 pointer。
- 新请求从 pointer 读取一次并把 revision/event 固定进 lookup boundary；运行中的 `REPEATABLE READ` 查询在并发切换及旧 snapshot 后续归档时仍读取请求开始时的完整旧快照，下一请求才看到新 active。
- 回滚只允许曾有 activation event、仍为 validated、具备要求 profile 的历史 snapshot。激活目标、embedding import 或 CAS 校验失败时，旧 active pointer 与状态保持不变。

### `0002 → 0003` 带数据升级

- migration 在 legacy assertions 与 bootstrap 前取得 `active_snapshot_pointers`、`corpus_snapshots` 的 `SHARE ROW EXCLUSIVE` 锁，阻止校验与约束安装之间发生 legacy 写入。
- 健康 legacy active pointer 被转换为 revision 1 的 `migration_bootstrap` event；bootstrap ID 对结构化 JSON 数组求 hash，scope/snapshot 中包含分隔符也不会产生字段边界歧义。
- 集成测试在独立临时 PostgreSQL 数据库先升级到 `0002_m3_immutable_rows`，构造两组旧拼接会碰撞的真实 active snapshot/pointer，再升级到 head，验证两个不同 event、pointer/event FK、timestamp 和 Alembic schema check。inconsistent legacy 数据继续失败关闭，不在 migration 中猜测或静默修复。

## 对抗审查结果

模块 B 与模块 C 审查均没有发现 P0 或 P1。以下 P2 为非阻塞后续优化，不改变已完成模块的验收结论：

1. retriever 在构造时会于 encoder 调用前完成 snapshot/profile/import receipt preflight；若 snapshot 在构造后被 archive，当前单次 `retrieve()` 会先编码，再由 repository 的查询期 context 复验拒绝。可在编码前再次做轻量 serviceability preflight，减少 snapshot 状态切换后的无效 provider 计算；现有实现不会返回 archived snapshot 数据。
2. `0002` 的关系闭包 trigger 可能一次锁定多个父 snapshot。后续可在 `FOR UPDATE` 前按 `snapshot_id` 显式 `ORDER BY`，为并发跨父关系写入提供确定锁顺序并进一步降低死锁概率；当前管理路径的 advisory lock 与测试未显示正确性缺陷。
3. PostgreSQL exclusion constraint 可以进一步增强同一 `law_id` 已核验版本的关键有效期重叠证明。当前 lookup 已在请求日期遇到多个有效版本时返回 `needs_disambiguation / overlapping_validity`，不会随机选择，因此不是错误答案缺口。
4. deferred activation consistency trigger 当前从全量 pointer/event 历史查找不一致项；后续可按触发记录的 scope 限定扫描以降低历史增长后的提交成本，不改变现有事务正确性。
5. `0003` 对 inconsistent legacy active pointer 明确失败关闭；最终门禁仍应把更多不一致负路径、downgrade 后旧行为和 re-upgrade 纳入自动回归。目前健康 legacy active pointer 和原分隔符歧义 case 已完成真实数据库升级验证。

本轮同时复验了 negative inner product 方向、稳定 tie、filter-before-limit、多 article 严格边界、typed provenance、artifact 兼容、snapshot/profile/import receipt、vector/payload hash、immutable trigger，以及 Hugging Face immutable revision 与 `trust_remote_code` 限制。
